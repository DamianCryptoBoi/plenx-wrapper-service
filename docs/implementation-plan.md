# Plenx wrapper implementation plan

Goal: a local FastAPI service and simple dashboard for multiple Plenx accounts and generation requests.

Design: serve plain HTML/CSS/JS from FastAPI. All API callers authenticate with a separate wrapper password in the Bearer header. Plenx account names and write-only tokens are stored in a private server SQLite database. Requests select stable account IDs via X-Account-ID; upstream requests use only the server's Plenx token. Jobs belong to stable account IDs, and status polling resolves the original account. A configured PLENX_WRAPPER_PASSWORD overrides the saved private password file. When both are absent, the first dashboard visit creates and confirms a password, saves it privately, and unlocks API access. Atomic first-time setup cannot overwrite an existing password. Dashboard passwords stay in page memory, and legacy browser credentials migrate to the server only after login, clearing each browser record after successful save. There is no background polling worker.

Preserve video server ID `56947b53-029e-4751-bbca-b9de54f5d628`; default model/aspect/duration/resolution are `omni-flash`, `16:9`, `4`, `720`. Image submission uses `/api/v1/queue/submit`, the supplied `image/gem-pix-2` nested JSON contract and server ID `dd597ae5-6ab3-4e76-9914-9da5589e21c1`; polling uses `/api/v1/queue/status/{task_id}`. Accept an explicit workplace UUID or resolve the account's `default_workplace_id` from `/api/v1/users/me` with the same token. The profile route also provides separate credit/free-credit/ruby balances and daily image usage to the dashboard; profiles stay in page memory, with refreshes once a minute, on manual refresh, and around generations.

Files: `main.py` owns routes, validation, upstream HTTP, and app lifecycle; `store.py` owns SQLite history; `static/` owns the dashboard; `tests/test_service.py` tests the API with a simulated upstream transport; `README.md` documents setup and curl requests.

Review findings for terminal failures and retaining older active jobs were reproduced and covered with regression tests. Real Plenx submission requires a user token and is not part of automated checks.

Constraints: Python >=3.11; FastAPI + HTTPX + python-multipart + Uvicorn, stdlib SQLite, hmac, and unittest; no frontend build pipeline. Bind localhost by default. The shared wrapper password grants all account use/management; no separate roles. Plenx tokens enter only through setup/replacement, are never returned or saved to browser storage, and persist in the private 0600 server database. Public docs and health expose no account data.
